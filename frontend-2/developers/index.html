Developers

API & CLI
Built On Direct+

Drive Clex from your terminal, scripts, or services. Sessions, status, pause, resume, and receipts are HTTP. The actual file bytes stay on the WebRTC channel between sender and receiver — never on our servers.

Privacy-first Direct-transfer-first No raw bytes on server
Architecture

HTTP for control,
WebRTC for bytes

Clex isn't a server-upload product. The HTTP API helps a sender and a receiver find each other and exchange WebRTC signaling, then they form a peer-to-peer DataChannel and send the file directly. The Clex server never sees raw file bytes in the normal flow.

Action Where it runs Why
Health probe HTTP /api/health Cheap liveness — safe for uptime monitors.
Create transfer (room code) Browser / CLI Generated client-side; signaling worker assigns the room when the first peer joins.
Connect peers Signaling worker (WebSocket) Relays SDP offers, answers, ICE candidates. Never sees file bytes.
Send file bytes WebRTC DataChannel (peer↔peer) 256 KB chunks, sliding window, ACK/retry, optional per-chunk hash.
Pause / resume / cancel DataChannel control message In-band control over the same P2P link, so latency is one round trip.
Receipt / proof Browser / CLI (computed locally) Built from the manifest + chunk tracker — no server-side ledger of file content.

Why a CLI, not curl uploads

A pure-HTTP curl upload would require the server to hold the file bytes — that's the model Clex deliberately avoids. To send a file from a terminal you need a peer that speaks WebRTC. That's the role of the Clex CLI: it plays the same DataChannel role the browser does, just headless. HTTP endpoints are still useful for health checks, room metadata, and (planned) reading a transfer receipt that you produced locally.

HTTP API

Stable today

These endpoints exist in the deployed API worker right now. Base URL is your Clex API origin (the same host that serves /api/health).

GET /api/health Stable

Liveness probe. Public, cacheable, no auth.

curl -s https://api.clex.in/api/health
{
  "ok": true,
  "service": "clex-api",
  "ts": 1714972800,
  "version": "phase-1-public-face",
  "bindings": { "kv": true }
}
GET /health Stable

Alias of /api/health. Use whichever your monitor prefers.

WS wss://signaling.clex.in/?room=<CODE>&mode=webrtc|local&chainId=<ID> Stable

The signaling worker is a WebSocket. Open one per peer. Send JSON envelopes ({"type":"offer","sdp":"..."}, {"type":"ice","candidate":...}). The worker forwards them to the other peer in the same room and disconnects when the room is empty. 

// minimal Node sender (uses 'ws' + 'wrtc' or a browser-like RTCPeerConnection)
const ws = new WebSocket(`wss://signaling.clex.in/?room=${code}&mode=webrtc&chainId=${id}`)
ws.onmessage = e => handle(JSON.parse(e.data))   // peer_joined / offer / answer / ice
ws.onopen = () => ws.send(JSON.stringify({ type: 'offer', sdp: localOffer.sdp }))
Planned

Coming next

These endpoints are designed but not yet shipped. They're additive — the existing API stays where it is. Anything that would touch raw file bytes is intentionally not on the list.

POST /api/transfer/sessions Planned

Reserve a room code so a sender and receiver can meet. The body is metadata only — file names, sizes, chunk count. No file bytes. Returns a transferId the CLI can later use to fetch the room's status from the signaling worker. 

curl -X POST https://api.clex.in/api/transfer/sessions \
  -H 'content-type: application/json' \
  -d '{ "fileNames": ["report.pdf"], "totalSize": 524288, "totalChunks": 2 }'

{ "transferId": "5d4e…", "roomCode": "K9M3JX", "expiresIn": 600 }
GET /api/transfer/sessions/:id Planned

Reads room metadata: peer count, mode (webrtc or local), and whether the room is open or sealed. Designed to power CLI clex status.

POST /api/transfer/sessions/:id/pause Planned

Convenience endpoint to send a pause control message to whichever peer is online. The actual pause is delivered over the DataChannel; this just lets you trigger it from a different process.

POST /api/transfer/sessions/:id/resume Planned

Same as pause but the inverse signal.

DELETE /api/transfer/sessions/:id Planned

Cancel an in-flight transfer and free the room.

GET /api/transfer/receipts/:id Planned

Returns the receipt the sender (or the CLI) uploaded for that transfer — file count, total size, chunk count, root hash, retries, health score. The receipt is a content-free summary; we never store the file itself.

CLI

Headless peer

The CLI is a real WebRTC peer. It opens the same DataChannel a browser would, runs the same Direct+ reliability layer, and produces the same receipt format. None of the file bytes leave the connection between you and your peer.

clex send ./report.pdf

Generate a 6-character room code, wait for the receiver, stream chunks over WebRTC. Pause with Ctrl+P, resume, or cancel anytime.

clex receive K9M3JX

Connect to a code, verify each chunk against the manifest, write to disk on success.

clex status <TRANSFER_ID>

Inspect a live or completed transfer: chunks, retries, health score, route, paused state.

clex pause <TRANSFER_ID>

Send the in-band pause signal to whichever peer is currently sending.

clex resume <TRANSFER_ID>

Inverse of pause. Picks up at the next pending chunk — no restart from byte zero.

clex receipt <TRANSFER_ID>

Print the local receipt: root hash, chunk count, retries, health.

clex doctor

Diagnose your network: STUN reachability, NAT type guess, signaling health.

Status: the CLI is in active development and tracks the same protocol version as the web client. Subscribe via the home page if you want a ping when it's installable.

Direct+ protocol

What's on the wire

Both peers exchange a capability message; if either side is on the legacy v0 client the transfer downgrades to plain streaming. Otherwise:

  1. Manifest. Sender posts a JSON manifest: file list, sizes, chunk size (256 KB by default), optional per-chunk SHA-256 hashes, optional root hash.
  2. Manifest ACK. Receiver verifies the shape and replies manifest_ack.
  3. Chunk frames. Sender writes binary frames with a 16-byte header (fileIndex / chunkIndex / chunkLength / flags). Receiver verifies length, ACKs immediately, then verifies hash off the hot path.
  4. Sliding window. Up to 32 chunks in flight per peer, gated by RTCDataChannel.bufferedAmount with a low-water trigger via bufferedamountlow. No "wait for one ACK before sending next chunk" — that's what made the previous build crawl.
  5. Retry. Up to 4 attempts per chunk, exponential backoff. On hash mismatch the receiver fires a chunk_nack and the sender re-queues that chunk.
  6. Pause / resume. Either peer can send pause over the same DataChannel; the send loop sleeps without dropping in-flight state. resume kicks the loop.
  7. Verify + receipt. Receiver counts chunks against the manifest, sends verify_success with the root hash, and both sides build a content-free receipt.
Boundary

What the API will never do

  • Accept raw file bytes over HTTP. The DataChannel is the only path file content takes.
  • Persist chunks server-side, even temporarily. There is no relay store.
  • Read filenames or content as part of the chain ledger. The chain only sees anonymous session metadata.
  • Add an "upload to Clex" endpoint that pretends to be P2P. If we ever ship a relay mode, it will be opt-in, separately documented, and clearly labelled — not bolted onto these routes.
